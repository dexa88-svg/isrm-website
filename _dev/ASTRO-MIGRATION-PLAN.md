# ISMR — Astro + MDX Migration Plan
**Status:** Planning  
**Author:** Den  
**Date:** 2026-05-19  
**Scope:** Full migration from static HTML to Astro 4 + MDX, unlocking every downstream item on the Phase 2+ roadmap.

---

## Why migrate now

The current static HTML site is working and deployed — that's good. But every next item on the roadmap (community CMS, ingestion pipeline, 3D models, AI chat, PWA) either requires a build step or becomes much harder without one. Astro solves this cleanly:

- Guides become `.mdx` files — editable by humans, writable by scripts, diffable in PRs (unlocks Community CMS and ingestion pipeline)
- Layouts become reusable components — one change propagates to all 50+ pages (unlocks consistent design evolution)
- Pagefind still runs at build time, same as now — no search regression
- Astro ships pure HTML — zero JS runtime overhead, SEO and Lighthouse scores stay the same or improve
- Astro Content Collections give you typed frontmatter — structured data for free, which the AI chat RAG pipeline needs

The migration is the biggest lift but it has a clean exit: at the end, the site still looks identical to users. All effort is architectural.

### URL strategy — zero redirects required

Astro's file-based routing mirrors the current structure exactly:

| Current URL | Astro source | Output URL |
|---|---|---|
| `/repair-guides/gy6-oil-change-guide.html` | `src/content/repair-guides/gy6-oil-change-guide.mdx` | `/repair-guides/gy6-oil-change-guide/` |
| `/diagnostics/gy6-no-start-troubleshooting.html` | `src/content/diagnostics/gy6-no-start-troubleshooting.mdx` | `/diagnostics/gy6-no-start-troubleshooting/` |

The `.html` extension is dropped in favour of clean URLs. Add one rule to `.htaccess` (or Hetzner's nginx config) to 301-redirect `.html` → clean URL. This is a one-liner and actually improves SEO.

If you want to keep `.html` extensions exactly as-is, Astro supports `trailingSlash: 'never'` + custom output filenames — but clean URLs are worth the trivial redirect work.

## MDX frontmatter schema

Each guide becomes a `.mdx` file with typed frontmatter. The Content Collection schema in `src/content/config.ts` enforces this at build time.

**Repair guide (`src/content/config.ts`):**

```typescript
import { defineCollection, z } from 'astro:content';

const repairGuides = defineCollection({
  type: 'content',
  schema: z.object({
    title: z.string().max(53),                  // 53 chars + " — ISMR" = 60 max
    description: z.string().min(150).max(160),  // SEO meta description
    publishDate: z.date(),
    updatedDate: z.date(),
    difficulty: z.enum(['Beginner', 'Intermediate', 'Advanced']),
    timeEstimate: z.string(),                   // e.g. "~30 min"
    tags: z.array(z.string()),
    appliesTo: z.array(z.string()),             // model/engine codes
    videos: z.array(z.object({
      id: z.string(),                           // YouTube video ID
      title: z.string(),
      creator: z.string(),
      position: z.enum(['hero', 'inline', 'related']),
    })),
    tools: z.array(z.string()).optional(),
    parts: z.array(z.object({
      name: z.string(),
      oemNumber: z.string().optional(),
      cost: z.string().optional(),
      affiliateUrl: z.string().url().optional(),
    })).optional(),
    sources: z.array(z.object({
      name: z.string(),
      url: z.string().url(),
    })),
    canonical: z.string().url(),
    draft: z.boolean().default(false),          // bot-draft flag for ingestion pipeline
    contributor: z.string().optional(),
  }),
});

export const collections = { 'repair-guides': repairGuides, /* ... */ };
```

## Component map (HTML → Astro)

Every repeated pattern in the current HTML becomes a component. This is what makes maintenance cheap going forward.

| Current HTML pattern | Astro component | Props |
|---|---|---|
| `<nav class="navbar">...</nav>` | `Navbar.astro` | `activePage` |
| `<footer class="guide-footer">...</footer>` | `Footer.astro` | `sources`, `updatedDate` |
| `<div class="video-embed">...</div>` | `VideoEmbed.astro` | `videoId`, `title`, `creator`, `caption?` |
| `<div class="callout callout-warn">` | `Callout.astro` | `type: 'warn'|'danger'|'tip'` |
| `<div class="source-box">` | `SourceBox.astro` | `sources[]` |
| `<div class="applies-to">` | `AppliesTo.astro` | `models[]` |
| Parts table | `PartTable.astro` | `parts[]` (with affiliate slot) |
| Breadcrumb | `Breadcrumb.astro` | `crumbs[]` |
| `<section class="page-hero">` | `PageHero.astro` | `title`, `meta`, `tags`, `appliesTo` |
| JSON-LD script | `JsonLd.astro` | `type`, `data` — rendered in `Base.astro` |
| GA4 script | Inlined in `Base.astro` | — |

The `Base.astro` layout handles everything that currently requires copy-pasting into each HTML file: GA4, favicons, meta description, OG tags, canonical, JSON-LD, CSS import. Writing a new guide will require zero boilerplate.

## Migration steps (in order)

### Step 1 — Scaffold Astro project (1–2 hours)

```bash
# In a new branch off main
npm create astro@latest ismr-astro -- --template minimal --typescript strict
cd ismr-astro
npx astro add mdx
```

Copy `public/styles.css` → `src/styles/global.css`. Import it in `Base.astro`.  
Copy `public/script.js` → `public/script.js` (stays in public, loaded as-is).  
Set `output: 'static'` in `astro.config.mjs` — keeps the same static-file deploy model.

### Step 2 — Build Base.astro and layouts (2–3 hours)

Build `Base.astro` first — it's the single file that replaces the copy-pasted `<head>` in all 50+ pages. Accepts props: `title`, `description`, `canonical`, `ogImage`, `jsonLd`.

Then build `Guide.astro`, `Diagnostic.astro`, `ModelPage.astro` — each wraps `Base.astro` and adds the section-specific chrome (page hero, breadcrumb, footer).

### Step 3 — Build shared components (2–3 hours)

Build in this order (each unblocks the next):
1. `Navbar.astro` + `Footer.astro`
2. `Callout.astro` + `VideoEmbed.astro` + `SourceBox.astro`
3. `PageHero.astro` + `Breadcrumb.astro`
4. `PartTable.astro` (include the affiliate URL slot from the start)

### Step 4 — Define Content Collections schema (1 hour)

Write `src/content/config.ts` with schemas for `repair-guides`, `diagnostics`, `models`, `parts`. Use strict Zod validation — it will catch frontmatter errors at build time before deployment.

### Step 5 — Migrate content (the big one — 4–8 hours, automatable)

For each HTML guide, extract the content and convert it to MDX. This is the most mechanical step and is a good candidate for a Claude scheduled task or a one-off script.

**Conversion strategy:**

Option A — Write a Node.js script that uses `node-html-parser` to extract structured sections (tools, parts, steps, videos) from the existing HTML and outputs MDX files with correct frontmatter. Run it once, then hand-clean the output. This is ~90% automated.

Option B — Convert manually, one guide at a time, starting with the simplest (oil change, spark plug) and finishing with the complex ones. Slower but produces cleaner output.

**Recommended: Option A for the body, Option B for QA.**

Script outline (`scripts/html-to-mdx.js`):
```javascript
// For each .html file in public/repair-guides/:
// 1. Parse with node-html-parser
// 2. Extract: title, meta description, canonical, tags from <head>
// 3. Extract: difficulty, timeEstimate from .guide-meta
// 4. Extract: appliesTo from .applies-to
// 5. Extract: video IDs from iframe src attributes
// 6. Extract: sources from .source-box links
// 7. Extract: main content from .guide-content as HTML
// 8. Convert HTML body → MDX using turndown (HTML→MD)
//    with custom rules for callouts, video-embeds, tables
// 9. Write frontmatter + MDX body to src/content/repair-guides/[slug].mdx
```

The wizard page (`diagnostics/wizard.html`) is interactive JS — keep it as a `.astro` page for now, migrate the logic to a client-side React island later (Astro supports this).

### Step 6 — Build listing pages (1–2 hours)

Each index page (repair-guides, diagnostics, models) becomes an `.astro` page that queries its Content Collection and renders a grid of cards. The filter/search on the listing page can remain client-side JS.

```astro
---
import { getCollection } from 'astro:content';
const guides = await getCollection('repair-guides', ({ data }) => !data.draft);
guides.sort((a, b) => b.data.updatedDate - a.data.updatedDate);
---
```

### Step 7 — Update generate-stats.js (30 min)

Change the script to count `.mdx` files in `src/content/repair-guides/` and `src/content/diagnostics/` instead of HTML files in `public/`. Everything else stays the same.

### Step 8 — Update GitHub Actions deploy (1 hour)

The deploy workflow gains a build step before the SFTP upload:

```yaml
- name: Install dependencies
  run: npm install

- name: Build Astro site
  run: npm run build        # astro build → outputs to dist/

- name: Generate stats
  run: npm run generate-stats

- name: Rebuild Pagefind index
  run: npx pagefind --site dist --output-path dist/pagefind

- name: Deploy to Hetzner
  run: # same SFTP curl loop, but upload dist/ instead of public/
```

`npm run build` must be added to `package.json` as `astro build`.

### Step 9 — Update scheduled task prompts (1 hour)

The three Claude scheduled tasks currently write HTML to `public/`. Update their prompts in `_dev/scheduled-tasks-updated/` to:
- Write new guides as `.mdx` to `src/content/repair-guides/`
- Use the frontmatter schema (all required fields)
- Set `draft: true` for bot-generated content (it won't publish until you remove the flag)
- Commit and push — the deploy workflow handles the rest

### Step 10 — Cutover (1 hour)

1. Merge the Astro branch to `main`
2. Verify GitHub Actions build succeeds and the deploy to Hetzner completes
3. Open the live site, spot-check 5–10 pages, run Lighthouse on mobile
4. Add the `.html` → clean URL redirect to `.htaccess`
5. Re-run `npm run generate-stats` to regenerate `sitemap.xml` with new clean URLs
6. Submit updated sitemap to Google Search Console

## What each roadmap item needs from this migration

This is the key strategic question — why do this first.

### 2. Community CMS (Decap/Sveltia)
**Needs:** MDX files in Git. Without the migration, a CMS editor would have to edit raw HTML, which is fragile and error-prone. With MDX + structured frontmatter, Decap CMS can render a clean form for every guide field. Unblocked immediately after Step 4.

### 3. Ingestion pipeline (YouTube/Reddit scraper)
**Needs:** A defined MDX schema to write into. The scraper's Claude pass maps raw content → frontmatter + MDX body. Sets `draft: true`. Creates a PR. None of this works against raw HTML. Unblocked after Step 4.

### 4. 3D exploded views (Three.js)
**Needs:** Astro's island architecture (`client:load`). You can drop a `<ThreeScene client:load />` React or Vanilla JS component into any `.mdx` file or `.astro` page. Doing this in static HTML requires hand-editing every page. Unblocked after Step 2.

### 5. AI repair assistant (RAG chat)
**Needs:** Structured content (frontmatter fields + clean MDX body) for the embedding pipeline. Parsing 50 HTML files is doable but messy. MDX with typed frontmatter makes the chunking strategy obvious: each step is a chunk, each guide is a document. Unblocked after Step 5.

### 6. PWA / mobile
**Needs:** A service worker and a `manifest.json`. These can be added to `public/` now (pre-migration), but the Astro `@astrojs/service-worker` integration makes cache strategy per-route trivial. Partially unblocked now, fully clean after migration.

### 7. Newsletter signup (Buttondown)
**Needs:** A reusable `NewsletterSignup.astro` component dropped into `Base.astro` footer. Without migration you'd edit 50+ HTML files. Unblocked after Step 2 (one component, one edit).

### 8. Affiliate links
**Needs:** `affiliateUrl` field in the `parts` frontmatter (already in the schema above). The `PartTable.astro` component reads this and renders the link. After migration, adding affiliate URLs is a frontmatter edit, not an HTML edit. Unblocked after Step 3.

## Recommended priority order (my take)

Here's why I'd do it in this sequence:

**1 → 7 → 8 → 2 → 3 → 4 → 5 → 6**

Run the Astro migration first (obviously). Once it's done, items 7 and 8 are each under an hour — newsletter and affiliate links are single-component additions that touch zero guide content. Do them immediately after cutover to start earning from the traffic you already have.

Then community CMS (item 2), because it makes every subsequent content task easier and starts building the contributor base. Then ingestion pipeline (item 3), which multiplies content velocity once contributions are flowing. Then 3D views (item 4) and AI assistant (item 5) — these are the features that make the site genuinely different from every other repair wiki, but they need a content base first. PWA (item 6) last — it's a polish layer, not a growth driver.

**The one exception:** if you're already seeing mobile users struggling with offline access, do PWA earlier. Check GA4 — if >60% of sessions are mobile, move PWA to position 3 or 4.

## Risks and mitigations

**Pagefind stops working.** Pagefind runs against built HTML output, not source files. As long as you run `pagefind --site dist` after `astro build`, it works identically. The existing `pagefind/` directory in `public/` becomes obsolete — remove it to avoid serving a stale index.

**Scheduled tasks break.** The three Claude tasks write to `public/` today. After migration they must write to `src/content/`. Update the prompts in Step 9 before merging to `main`. Until then, run the Astro branch separately.

**SEO regression from URL changes.** The `.html` extension drop changes URLs. 301 redirects in `.htaccess` + updated sitemap = no lasting impact. Temporary 1–2 week ranking dip possible. Acceptable trade-off.

**Content loss during conversion.** Run the HTML-to-MDX script on a copy. Keep the original HTML files in a `_archive/` folder until you've verified every page visually after cutover.

**Interactive wizard.** `diagnostics/wizard.html` uses complex client-side JS. Migrate it as a `.astro` page that loads the existing `wizard.js` as a `<script>` tag. Full conversion to an Astro island is Phase 2.
